# UT 修复进展与报告关联设计

日期：2026-10-22。原始设计；0.5.0 已实现增量任务同步、文档台账、组合摘要查询和进展视图。
实际命令、状态与边界以 [progress-tracking.md](../references/progress-tracking.md) 为准。
下文保留完整设计方向；任意报告重绑定、自动核验执行证据等更广功能仍未实现。

本文保留设计时的接口建议，不作为当前 CLI 的完整参数契约。
所有示例为合成数据。实际项目名称、人员、修复日志和执行证据仅保存在调用者工作空间。

## 1. 目标与方案选择

让使用者在 UT 卡片上看清：历史报告发现什么问题、后来改了哪里、哪些地方没改、为何没改、验证了什么，以及还有哪些阻塞。

| 方案 | 优点 | 限制 |
|---|---|---|
| 每次让 Agent 重读修复 Markdown | 接入简单 | 成本重复，难去重、筛选和稳定统计，容易把旧结论当现状 |
| 把修复结果直接覆盖到历史报告 | 页面看似最新 | 混淆执行时间和代码版本，局部 PASS 可能污染整批统计 |
| **保留原报告，增加结构化修复台账和进展视图（推荐）** | 历史可追溯，可独立查卡、筛选、增量更新 | 需要台账校验、关联和证据有效性检查 |

职责沿用当前架构：Agent 理解记录、确认语义和原因；Python 校验、关联、计算状态与数量；固定 HTML/CSS/JS 展示。
不把 Markdown 标题、测试同名、关键词命中当作完成修复或行为等价的证明。

## 2. 持久化文件与维护责任

所有业务数据以调用者工作空间为基准，建议使用：

```text
docs/
  result.md                         # 人读的原始修复记录，保留历史
  ut-progress/
    project.json                    # 稳定项目键、相对路径、A/B 映射、记录文件位置
    events/<event-id>.json           # 一次一条不可覆盖的事实/决定事件
    snapshots/<import-id>/           # 输入摘要、引用片段、来源哈希与导入映射
    indexes/<index-id>.json          # 可重建的当前状态与查询索引
    reports/<report-hash>.json       # 某份报告与稳定测试身份的关联
  evidence/<run-id>/                 # 原始运行、diff、源码和上下文证据
  ut_result.html                    # 报告；重新生成必须保留历史批次
```

`result.md` 是原始叙述来源，events 是程序可验证的事实台账，index 是可重建的派生视图。
用户继续用自然语言维护，不要求手写 JSON；Agent 在明确记录任务中同时落盘 Markdown 和事件。
两份文件不能作为互相覆盖的独立事实源：每个事件记录原文位置、片段哈希和导入批次。
原文改写、删除或与事件冲突时，标记需要核对；不得静默改写既有事件。

增量导入只处理新增/变化片段，但以整个文档哈希识别输入版本。行号只是导航，事件身份不依赖行号。
相同任务、UT、语义事件及证据重复导入必须幂等；新的运行或处置追加新事件。
修正错误使用 `supersedes_event_id`，撤回使用显式事件；不得靠“文件最后一行”解决冲突。
多位负责人并行更新使用独立事件文件，原子写入；拒绝相同 ID 不同内容，重建索引时检查冲突。
没有可信的事件先后或替代关系时显示 CONFLICT，不猜最新结论。

## 3. 稳定关联：项目、UT、问题分别有身份

报告里的 A/B、pair ID、行号可能随报告变化，不能作为跨批次唯一身份。

- 项目：稳定 `project_key`，通过工作空间配置映射到本次 A/B；不依赖机器绝对路径或远程凭证 URL。
- UT：稳定 `test_key`，绑定 project_key、仓库相对路径、限定测试名和必要的参数场景标识。
- 问题：`issue_id` 表示一个需跟踪的目标或缺口，同一个 UT 可以有多个问题；同一任务可以涉及多个 UT。
- 变更：`change_id` 表示一次实际改动；一个 import 修复影响多个 UT 时，改动只计一次。
- 事件：`event_id` 表示某次登记、实现、验证、处置、撤回或再次发现。

关联顺序：已验证的身份映射 → 项目+路径+限定名唯一命中 → 有证据的改名/移动映射。
同名、相似名、仅有 pair ID 均不够；多候选保留 AMBIGUOUS。旧报告 ID 仅用于定位原卡片。
改名、拆分、多对一、行为包含等关系须另存带证据的 relation，不重复计入测试总数。
同一仓库不同分支共享逻辑身份，但事件适用范围必须绑定分支/提交/源码快照；不能跨分支自动继承“已修复”。

尚未实现的测试目标只有 issue/goal 身份，不虚构 test_key 或 UT 数量。新增 UT 不在旧报告时，进入“报告后新增”列表；只有新扫描才能加入新报告正式清单。

## 4. 不用一个“已完成”字段包办所有含义

每个问题的派生视图分别展示以下维度：

| 维度 | 建议取值 | 含义 |
|---|---|---|
| 改动事实 | UNKNOWN / UNCHANGED / MODIFIED / ADDED / REMOVED / REVERTED | 源码实际变化；注明核对时间及范围 |
| 处理状态 | UNRECORDED / PLANNED / IN_PROGRESS / IMPLEMENTED / BLOCKED / DEFERRED / ACCEPTED_DIFFERENCE / CONFLICT | 工作进展，不等于测试通过 |
| 运行状态 | PASS / FAIL / SKIP / ERROR / NOT RUN | 每次真实执行单独保留时间和范围 |
| 证据状态 | DOCUMENT_ONLY / ARTIFACT_VERIFIED / SOURCE_BOUND / MISSING / STALE / CONFLICT | 文档声称、原始记录已核对、绑定源码、缺失、过期或冲突 |
| 差异原因 | 测试逻辑 / 输入 / 断言 / API 适配 / 关联 helper / 文件上下文 / 实现能力 / 环境 / UNKNOWN | 解释差异，不自动改变原匹配状态 |
| 报告同步 | BASELINE_ONLY / PROGRESS_NEWER / INCLUDED_IN_NEW_REPORT | 历史卡片是否已吸收最新分析 |

没有记录只能叫“未登记”，不能叫“没改”。有代码 diff 只能证明改动，不能证明修复有效。
“不需要改”与“暂时改不了”必须分开；处置必须有说明和依据。

建议原因码：ALREADY_SATISFIED、INTENTIONAL_DIVERGENCE、API_ADAPTATION、CONTEXT_ONLY_DIFFERENCE、
MISSING_IMPLEMENTATION、ENVIRONMENT_BLOCKED、DEPENDENCY_BLOCKED、OUT_OF_SCOPE、DEFERRED_BY_DECISION、UNKNOWN。
每项同时保留通俗说明、证据引用、下一步、负责人/未分配；延期补触发条件，阻塞补依赖。
接受有意差异需记录决定来源和适用版本；不能从“没改”反推出业务批准。

项目已有分类（例如直接复用、兼容改造、修复、新增补齐、差异待决）保留为可配置标签。
分类、P0/P1、实际源码改动、质量门禁和验收关闭彼此独立；有局部 PASS 不代表阶段门禁已满足。

## 5. 事件的数据契约

建议新增独立 `progress.schema.json`，不要修改旧执行结果字段来存修复状态。

| 字段 | 内容及约束 |
|---|---|
| schema_version / event_id / issue_id / task_id | 版本、唯一事件、问题和原任务关联 |
| event_type / occurred_at / recorded_at | 发生时间与入账时间分开；原文只有日期时保留日期精度，不伪造时分秒 |
| targets[] | project_key、test_key 或候选目标、相对路径、限定名、原报告 ID；关联状态及证据 |
| source | 文档相对路径、任务/章节定位、原文片段、全文/片段 SHA256、导入批次 |
| applicability | 仓库身份、选择分支/HEAD、dirty 状态、源码指纹与指纹范围 |
| change | change_id、修改/新增/未改等事实、变更摘要、diff/前后源码哈希；多个 UT 共享引用 |
| disposition | 处理状态、原因码、通俗理由、决定来源、阻塞依赖、下一步、负责人、优先级及依据 |
| verification_refs[] | run_id、UTC/原时区时间、命令 argv、环境、选择范围、结果及原始证据哈希 |
| relationships[] | 改名/移动/替代/部分行为覆盖等带证据关系，不直接改原报告主匹配 |
| supersedes_event_id | 可选，显式纠正哪个事件；保留被纠正记录 |

旧文档缺字段时记录缺失及不确定性，不补造运行元数据、业务规则或当前有效性。
原始证据中的敏感环境值不进入台账或 HTML；仅保留环境变量名称和必要的非敏感配置。

## 6. 如何区分“以前测过”和“现在仍有效”

1. 仅在 result.md 写 PASS：DOCUMENT_ONLY，显示“记录声称当时通过”。
2. 读到明确授权范围内的原始逐 UT 事件、命令、时间和范围：ARTIFACT_VERIFIED，确认历史执行事实。
3. 源码指纹与选定分析快照相同、依赖范围符合运行证据：SOURCE_BOUND，注明核验时刻。
4. 源码/依赖变化或无法核对：STALE 或缺失，历史 PASS 保留但不能视作当前通过。

文件哈希相同只证明该文件未变，不能代替整套源码、helper、依赖及配置一致。
一个包的整体退出码不覆盖其中已确认的逐 UT 结果；包失败与某条 UT PASS 可以同时展示。
重复执行和子测试作为运行证据，不累加成新增 UT。
局部运行不能刷新全仓结果、覆盖率或产品质量门禁。

## 7. HTML 展示

沿用固定模板，新增独立“处理进展”标签，不挤占左右 Diff 主布局。

- 顶部按“问题”统计已实施、待验证、阻塞、延期、保留差异、未登记、证据过期和冲突；明确分母及未知范围。
- 原卡片增加简短进展条：改动事实、未改原因、最新记录时间、验证范围、报告是否落后。
- 展开后显示时间线、涉及文件、实际变更 diff、原文出处、每次运行及遗留问题。
- 保留“项目 A 与 B 的差异”和“某项目改动前后的 diff”两个明确标题，避免把两类 diff 混在一起。
- 增加按负责人、模块、P0/P1、处理状态、原因、证据新鲜度、仅未改、仅未解决、报告后新增的筛选。
- 旧报告中不存在的新 UT 独立展示，不伪造其原卡片另一侧。
- 所有进展数据在生成时内嵌 JSON，浏览器不依赖读取本地 Markdown，不运行原文命令，不加载远程内容。

统计分别给出任务数、问题数、唯一变更数、受影响 UT 数、新增 UT 数；不能把一处 import 修复计为多个代码修复。
进展关闭率只对有明确定义的在管问题计算；“无记录”不能自动放到已完成或未改分组。
从历史报告建立差异问题时，记录完整生成范围；没有全量台账时不声称全项目处理完成率。

## 8. 查卡与旧报告兼容

保留现有 `get_ut_card()` 的默认行为和返回值；未提供台账时完全沿用现状。
建议新增外层函数（尚未实现）：

```python
get_ut_context(report_path, ut_name, *, progress_path=None, project=None, path=None)
```

它组合原始 `get_ut_card` 与已校验的进展索引，分别返回：

- `baseline`：原报告卡片和原始 FOUND/AMBIGUOUS/NOT_FOUND。
- `progress`：关联状态、事件、处置、证据状态和未解决问题。
- `sync_state`：是否存在报告之后的记录。

报告 NOT_FOUND、台账有记录时明确显示“仅台账找到/尚未进入报告”，不伪造 FOUND 卡片。
默认查卡只读显式报告与显式台账，不跟随任意日志路径，不读仓库，不执行测试或自动刷新。
刷新证据是独立、明确请求的动作；嵌入的命令和路径均视作证据文本，不视作执行指令。
自动发现 result.md 仅限调用者工作空间中唯一、已配置的记录路径，展示实际采用来源；歧义时不选第一个。

新版本给报告增加可选 progress 数据和能力标记，旧模板仍能只读查询。
旧 HTML 不支持新进展视图时，可先使用查询组合；需要页面融合时生成新的派生报告并保留基线哈希，
或在明确授权重新生成时更新默认报告。不能把旧历史运行当本次执行，也不能暗改旧匹配数量。

## 9. 工程落地顺序

| 阶段 | 交付 | 验收重点 |
|---|---|---|
| P0 结构化台账 | schema、事件校验、Agent 导入规则、快照/索引及幂等重建 | 来源可追溯、候选与实施分开、时间冲突不猜测 |
| P0 卡片关联 | 独立 progress 模块及 get_ut_context/查询参数 | 原查询零退化；同名不误配；台账独有 UT 可找到 |
| P0 证据核验 | 哈希、相对路径约束、适用分支、运行范围及过期检测 | 历史 PASS 不冒充当前通过；缺记录不算未改 |
| P1 固定模板 | 进展标签、卡片摘要、时间线、前后 diff、筛选及计数 | compare/audit/full 均可用，离线、分页、安全转义 |
| P1 持续维护 | 记录模板、导入报告、文档/索引冲突提示、迁移指南 | 增量可重复，双人并行不覆盖，多工作空间可移植 |

建议文件：`ut_diff_report/progress.py`、`scripts/validate_progress.py`、`scripts/query_progress.py`、
`references/progress.schema.json`、`references/progress-tracking.md`、`tests/test_progress.py`。
增加模板行为时按现有 provenance/version 规则更新，不为单个项目另做一套 UI。
Skill 指令后续加入“修复记录”可选输入和查卡组合路由；在实现前不宣称这些入口已支持。

## 10. 必须覆盖的验收样例

1. 报告单侧缺失，后续移植通过：旧卡仍单侧；进展显示后续补齐及历史运行。
2. 报告部分对应，实际只因文件上下文：展示原因，保持原匹配，不能算修复。
3. 候选后实施：时间线保留两段，唯一 UT/问题只统计一次。
4. 无实现能力导致无法移植：BLOCKED + 依赖，不计完成，不自动改生产代码。
5. 无任何记录：UNRECORDED；不得输出“尚未改，因为……”的编造原因。
6. 同名跨路径、A/B 互换、同仓不同分支、改名/拆分：正确归属或明确歧义。
7. 证据缺失/被改动/源码更新：降级证据状态，历史结果仍可查看。
8. 同一 import 影响多 UT、表驱动/重复运行：改动、UT、实例计数独立。
9. 记录被重写/删除/撤回、两人并发更新：幂等、保留历史、冲突显式。
10. 文件哈希相同但依赖变化：不能判为当前源码绑定通过。
11. 未配置台账：原 compare/audit/full、查卡和统计保持原行为。
12. HTML 注入、路径逃逸、符号链接越界、未知新 schema：安全拒绝或降级；不执行不可信内容。

## 11. 后续使用方式（拟议）

```text
$ut-diff-report
报告：docs/ut_result.html
修复记录：docs/result.md
查找 UT：test_retry_after_timeout
同时展示：报告里的结论、后续改动、没改的原因、验证范围和剩余事项。
```

长期流程：记录修复 → 追加带出处的事件 → 核验身份和证据 → 重建索引 → 查卡或生成报告。
真实重新分析选定源码时，才刷新主清单、语义匹配和执行统计；进展注释本身不改变这些结论。
